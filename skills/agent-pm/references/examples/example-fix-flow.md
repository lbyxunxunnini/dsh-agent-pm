- APM-INSTRUCTION-001 [P1] 角色定义缺失"不做的事"边界 → accepted
- APM-WORKFLOW-001 [P1] 任务拆解后缺少确认步骤 → accepted
- APM-INSTRUCTION-002 [P2] 触发条件描述有歧义 → deferred
- APM-WORKFLOW-002 [P2] 子任务执行失败时无回退机制 → deferred

## 修复计划

```
## 修复计划（共 3 项）

### 必须修复
1. APM-LOGIC-001 [P0] 子任务依赖关系未处理 → 无依赖（先修）
   - 验收条件：
     a. 拆解阶段输出子任务依赖图
     b. 执行阶段按依赖顺序排列
     c. 循环依赖时有检测和报错

2. APM-INSTRUCTION-001 [P1] 角色定义缺失"不做的事"边界 → 无依赖
   - 验收条件：
     a. SKILL.md 中存在"不做的事"章节
     b. 章节包含至少 3 项明确的边界声明
     c. 边界声明与角色定义不矛盾

3. APM-WORKFLOW-001 [P1] 任务拆解后缺少确认步骤 → 依赖 APM-LOGIC-001（依赖图完成后才能确认）
   - 验收条件：
     a. 流程图中存在"用户确认"步骤
     b. 该步骤在"拆解"和"执行"之间
     c. 用户拒绝时有重新拆解的路径

### Backlog（本轮不阻塞）
4. APM-INSTRUCTION-002 [P2] 触发条件描述有歧义 → status: deferred
5. APM-WORKFLOW-002 [P2] 子任务执行失败时无回退机制 → status: deferred
6. APM-DESIGN-001 [P2] 输出格式未定义 → status: deferred
7. APM-GOVERNANCE-001 [P2] 缺少任务完成的验收标准 → status: deferred

→ 确认修复顺序？(Y/n/调整)
```

用户确认：Y

## 修复过程

### Step 1: 修复 APM-LOGIC-001

**修改文件**: SKILL.md

**修改内容**:

```diff
## 任务拆解

接收用户任务后，按以下步骤拆解：

1. 识别任务目标
2. 拆解为子任务（每个子任务独立可执行）
3. +识别子任务依赖关系，生成依赖图
4. 检测循环依赖，如有则报错并要求用户重新描述任务
5. 按依赖顺序排列子任务

+### 依赖图格式
+
+```json
+{
+  "tasks": [
+    {"id": "t1", "name": "创建数据库", "depends_on": []},
+    {"id": "t2", "name": "创建 API", "depends_on": ["t1"]},
+    {"id": "t3", "name": "创建前端", "depends_on": ["t2"]}
+  ]
+}
+```

## 执行

+按依赖图顺序执行子任务。每个子任务执行前检查前置依赖是否完成。
```

**L2 自检**:
- [x] 依赖图格式定义完整
- [x] 循环依赖检测已添加
- [x] 执行顺序与依赖图一致

**L3 引用检查**:
- [x] 依赖图格式与输出格式一致
- [x] 无其他文件引用此逻辑

### Step 2: 修复 APM-INSTRUCTION-001

**修改文件**: SKILL.md

**修改内容**:

```diff
## 角色定义

你是任务驱动助手，帮助用户拆解复杂任务并逐步执行。

+## 不做的事
+
+- 不做代码实现：只拆解任务，不写代码
+- 不做架构设计：只执行任务，不设计系统架构
+- 不做决策替代：只提供拆解方案，不替用户做决策
+- 不做质量保证：只执行任务，不保证代码质量（那是 code review 的事）
```

**L2 自检**:
- [x] "不做的事"章节存在
- [x] 包含 4 项边界声明（≥3）
- [x] 边界声明与角色定义不矛盾

**L3 引用检查**:
- [x] 无其他文件引用角色定义

### Step 3: 修复 APM-WORKFLOW-001

**修改文件**: SKILL.md

**修改内容**:

```diff
## 执行流程

1. 接收任务
2. 拆解子任务
3. 生成依赖图
4. +展示拆解结果给用户确认
5. +用户确认后进入执行
6. +用户拒绝则返回步骤 2 重新拆解
7. 按依赖顺序执行子任务
8. 汇报执行结果

+### 用户确认格式
+
+向用户展示：
+1. 子任务列表（含依赖关系）
+2. 预估执行时间
+3. 确认提示："以上拆解是否正确？(Y/n/调整)"
```

- [x] 用户拒绝时有重新拆解路径

**L3 引用检查**:
- [x] 确认格式与依赖图格式一致
- [x] 无其他文件引用此流程

## 关键观察

1. **修复顺序很重要** — APM-LOGIC-001 必须先修，因为 APM-WORKFLOW-001 依赖它
2. **验收条件要具体** — 每个条件都可以明确判断通过/不通过
3. **L2 自检 + L3 引用检查** — 确保修改不引入新问题
4. **diff 驱动验证** — 只验证已确认问题，不重新开放式审查
