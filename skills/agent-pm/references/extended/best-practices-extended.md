# Agent 项目最佳实践 - 扩展模式

> 本文件包含 best-practices.md 中的扩展模式，按需加载。

---

## BP-003: Process Flow Diagram

用 `digraph`（Graphviz DOT 语法）画出工作流的完整流程图，包括判断节点、分支、循环、终止状态。流程图让 agent 能快速定位自己在流程中的位置，减少"我现在该做什么"的困惑。

**审查检查点**：
- [ ] 多步工作流（3 步以上）是否有可视化流程图？
- [ ] 流程图是否包含所有判断节点和分支？
- [ ] 流程图是否标明了循环和终止条件？
- [ ] 流程图与文字描述是否一致（不矛盾）？

**修复建议**：为项目的主工作流添加 digraph 流程图，放在工作流章节的开头。

## BP-004: 可复用 Prompt 模板作为独立文件

将 agent 调用 subagent 或生成报告时使用的 prompt 模板提取为**独立文件**，主文件只引用它们。

**好处**：
- 主文件瘦身，降低 token 消耗
- 模板可独立更新，不影响主逻辑
- 多处引用同一模板时保持一致

**审查检查点**：
- [ ] 项目是否有重复使用的模板/格式定义？
- [ ] 这些模板是否内联在主文件中导致主文件过长？
- [ ] 模板是否可以提取为独立 reference 文件？

**修复建议**：将主文件中超过 10 行且被多处引用的模板提取到 `references/` 目录下，主文件用一句链接引用。

## BP-005: Skill/Mode 类型标注（Rigid vs Flexible）

将 skill 或工作流模式明确标注为两种类型之一：
- **Rigid**：严格遵循，不允许 adapt、不允许"看情况"简化
- **Flexible**：可以适应上下文，agent 可以根据实际情况调整执行方式

**审查检查点**：
- [ ] 项目中的关键流程是否标注了 Rigid/Flexible 类型？
- [ ] 标注是否准确？
- [ ] agent 是否知道 Rigid 流程不可 adapt？

**修复建议**：在每个关键流程/模式的标题处添加 `[Rigid]` 或 `[Flexible]` 标注。

## BP-006: Description Field 纪律

skill 的 description 字段**只描述触发条件**（什么时候用），**不描述工作流**（用了之后做什么）。

**原因**：测试表明，description 中包含工作流摘要会导致 agent 走捷径——看到 description 就"知道"流程，从而跳过实际读取 skill 内容的步骤。

**审查检查点**：
- [ ] skill 的 description 是否只描述触发条件？
- [ ] description 中是否包含了工作流摘要？
- [ ] description 是否以"Use when..."或等效的触发条件开头？

**修复建议**：精简 description 为纯触发条件，去除所有工作流描述。

## BP-007: 连续执行 + 智能暂停

agent 在执行多步任务时，采用"连续执行"模式：
- **默认不暂停**：不在每步之间征求用户确认
- **智能暂停点**：只在特定条件触发时暂停（失败、阻塞、需要用户决策、发现回归）

**审查检查点**：
- [ ] 多步执行流程是否默认连续执行而非逐步确认？
- [ ] 是否有明确的智能暂停条件？
- [ ] 暂停条件是否覆盖了安全关键点？

**修复建议**：将逐步确认改为连续执行 + 智能暂停：定义 3-5 个暂停条件，其他情况自动继续。

## BP-009: 设计先行门控（Design-First Gate）

在任何实现代码之前，必须先完成**设计探索并获得用户批准**。这是一个 HARD-GATE——不通过就不能写代码。

**审查检查点**：
- [ ] 项目是否有"先设计后实现"的明确流程？
- [ ] 该流程是否有 HARD-GATE 阻断机制？
- [ ] 设计阶段是否包含需求澄清和方案比较？

**修复建议**：在实现流程前插入设计阶段，用 HARD-GATE 标签阻断。

## BP-010: 两阶段 Review（先规格合规，再代码质量）

代码审查分为**两个独立阶段**：
1. **规格合规审查** — 代码是否实现了设计/需求中要求的所有东西？
2. **代码质量审查** — 代码写得好不好？

**审查检查点**：
- [ ] 项目是否有代码审查/质量检查流程？
- [ ] 审查是否区分了"规格合规"和"代码质量"两个维度？
- [ ] 两个维度的审查顺序是否正确（先规格后质量）？

**修复建议**：将单一 review 拆为两阶段：先检查"做对了没有"，再检查"做好了没有"。

## BP-011: 小任务 + 新鲜上下文

将大任务拆分为**小任务**（每个 2-5 分钟可完成），每个小任务用**全新的 subagent** 执行。

**好处**：
- 避免上下文污染
- 每个 subagent 只需要理解当前任务的上下文
- 并行安全
- 失败隔离

**审查检查点**：
- [ ] 大任务是否被拆分为可独立执行的小任务？
- [ ] 每个小任务是否使用独立的执行上下文？
- [ ] 任务间是否有明确的输入/输出边界？

**修复建议**：将大流程拆分为独立的小任务，每个任务有明确的输入、输出和验证标准。

## BP-012: 阶段间结构化交接

工作流的每个阶段之间有**明确的交接条件和触发方式**。

**交接条件包括**：
- 前置阶段必须完成的产出物
- 交接时的触发动作
- 不满足交接条件时的处理

**审查检查点**：
- [ ] 工作流各阶段之间是否有明确的交接条件？
- [ ] 交接条件是否包含前置产出物和触发动作？
- [ ] 不满足交接条件时是否有明确的处理路径？

**修复建议**：为工作流的每个阶段定义：产出物 → 交接条件 → 下一阶段触发动作。

## BP-016: 目标治理优先（Goal Governance over Process Control）

项目的规则/约束中，帮助 Agent 理解目标的规则应占相当比例，而非全部是限制 Agent 行为的规则。

**核心要素**：
- 每条规则可以问："是在帮 Agent 理解目标，还是在限制行为？"
- 目标治理类规则占比不低于 20-30%
- 不在过程控制上无限叠加，优先强化目标端

**审查检查点**：
- [ ] 统计项目中所有"必须/禁止/不得"类规则的数量
- [ ] 统计项目中"目标/验收/品质/评估"类规则的数量
- [ ] 比例是否严重失衡（如过程控制 > 80%）？

**修复建议**：审查现有规则，将纯过程控制类规则考虑精简或合并，增加目标治理类规则。
